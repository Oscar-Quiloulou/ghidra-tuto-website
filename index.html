Guide Ghidra Complet

Maîtriser le reverse engineering avec Ghidra : installation, utilisation, debugging, scripting, et solutions aux problèmes rencontrés en environnement restreint.

Introduction

Ghidra est un framework de reverse engineering développé par la NSA, publié en open source en 2019. Il permet d'analyser des binaires compilés et de reconstruire du pseudo-code à partir d'assembleur. Il est comparable à IDA Pro ou radare2, mais entièrement gratuit et extensible.

Capacités principales : désassemblage, décompilation, graphes, scripting (Java/Python), debugging, version tracking, analyse comportementale (BSim), et bien plus.

⚠️ Avertissement légal N'analyse que des binaires que tu possèdes, que tu as écrits, ou pour lesquels tu as une autorisation explicite (CTF, crackmes.one). Le reverse engineering de logiciels tiers peut violer les conditions d'utilisation ou la loi selon les pays.

1. Installation & prérequis

Systèmes supportés

Ghidra fonctionne sur Windows, macOS et Linux. Il nécessite un JDK 17 ou 21 selon la version de Ghidra.

Version GhidraJava requisClass file version
Ghidra 10.xJava 11+55

⚠️ Important Java est rétrocompatible : Java 25 peut exécuter du bytecode compilé pour Java 21. Tu peux donc utiliser un JDK 25 pour Ghidra 12.x sans problème. C'est l'inverse qui ne fonctionne pas (Java 8 ne peut pas exécuter du bytecode Java 21).

Installation pas à pas

  1. Installe un JDK : sudo apt install openjdk-21-jdk (Linux) ou télécharge Adoptium (Windows/macOS).
  2. Télécharge Ghidra depuis ghidra-sre.org ou la page GitHub officielle.
  3. Décompresse l'archive dans un dossier (pas d'installeur).
  4. Lance ghidraRun (Linux/macOS) ou ghidraRun.bat (Windows).
  5. Accepte la licence et choisis ton répertoire de travail.
✅ Nouveauté Ghidra 11.3+ Le support Python 3 natif via PyGhidra est désormais intégré. Plus besoin de Jython pour les scripts modernes.

2. Importer un binaire

  1. Crée un projet : File → New Project → Non-Shared Project.
  2. Choisis un dossier et un nom de projet.
  3. File → Import File et sélectionne ton binaire (.exe, .elf, .so, .dll, .bin…).
  4. Ghidra détecte le format automatiquement. Vérifie l'architecture et clique OK.
  5. Double-clique sur le fichier importé pour ouvrir la vue d'analyse.
💡 Astuce Pour les binaires avec debug info, Ghidra importe automatiquement les symboles et types DWARF, ce qui améliore considérablement la qualité du décompilé.

3. Analyse automatique

À l'ouverture, Ghidra propose la fenêtre Analyze. Accepte avec les options par défaut pour un premier passage. L'analyse effectue :

  • la détection des fonctions et de leurs bornes,
  • la reconstruction des chaînes de caractères,
  • l'identification des appels de bibliothèques,
  • la propagation des types et des symboles,
  • la détection des constantes cryptographiques.
Binaire volumineux ? Décoche les analyseurs lents (Decompiler Parameter ID, Aggressive Instruction Finder) pour un premier passage rapide.

Re-analyser après modification

Si tu modifies des types ou des signatures : Analysis → Re-analyze Selection.

15. Installation sans droits admin & contournement de restrictions

Sur un poste d'entreprise ou une machine verrouillée, plusieurs restrictions peuvent empêcher Ghidra de démarrer :

  • Pas de droits administrateur
  • cmd.exe bloqué par stratégie de groupe
  • Fichiers .bat et .cmd bloqués (AppLocker, SRP, WDAC)
  • java.exe bloqué par contrôle parental ou autre
  • Windows PowerShell soumis à une ExecutionPolicy restrictive

Stratégie générale

PowerShell est presque toujours disponible même quand cmd.exe est bloqué. On va donc réimplémenter entièrement ghidraRun.bat en PowerShell, sans jamais invoquer cmd.exe.

⚠️ Pourquoi ne pas juste appeler le .bat depuis PowerShell ? Si le blocage est fait par AppLocker/SRP/WDAC, c'est le noyau Windows qui refuse d'exécuter un .bat, peu importe qui l'appelle. Il faut rejouer la logique du script en pur PowerShell.

function Get-JavaMajorVersion {
    param([string]$JavaExe)

    # On lance Java via System.Diagnostics.Process pour contourner
    # complètement la gestion d'erreur de PowerShell (java -version
    # écrit sur stderr, ce qui déclenche $ErrorActionPreference = "Stop").
    try {
        $psi = New-Object System.Diagnostics.ProcessStartInfo
        $psi.FileName               = $JavaExe
        $psi.Arguments              = "-version"
        $psi.RedirectStandardError  = $true
        $psi.RedirectStandardOutput = $true
        $psi.UseShellExecute        = $false
        $psi.CreateNoWindow         = $true

        $proc = [System.Diagnostics.Process]::Start($psi)
        $stderr = $proc.StandardError.ReadToEnd()
        $stdout = $proc.StandardOutput.ReadToEnd()
        $proc.WaitForExit()

        $combined = $stderr + "`n" + $stdout

        if ($combined -match 'version\s+"(\d+)') {
            $major = [int]$Matches[1]
            # Cas spécial : "1.8.0_xxx" → on veut 8, pas 1
            if ($major -eq 1 -and $combined -match 'version\s+"1\.(\d+)') {
                $major = [int]$Matches[1]
            }
            return $major
        }
    } catch { }

    return 0
}

function Resolve-JavaPath {
    param([string]$InputPath)

    if (-not $InputPath) { return $null }
    if (-not (Test-Path $InputPath)) { return $null }

    $item = Get-Item $InputPath -ErrorAction SilentlyContinue
    if (-not $item) { return $null }

    if ($item.PSIsContainer) {
        $c1 = Join-Path $item.FullName "bin\java.exe"
        if (Test-Path $c1) { return $c1 }

        $c2 = Join-Path $item.FullName "bin\javaw.exe"
        if (Test-Path $c2) { return $c2 }

        $binDir = Join-Path $item.FullName "bin"
        if (Test-Path $binDir) {
            $exclude = @('javac.exe','jar.exe','jarsigner.exe','javadoc.exe','jdb.exe',
                         'jps.exe','jstat.exe','jcmd.exe','jconsole.exe','jlink.exe',
                         'jmod.exe','jrunscript.exe','jshell.exe','keytool.exe',
                         'policytool.exe','rmid.exe','rmiregistry.exe','serialver.exe',
                         'jaccessinspector.exe','jaccesswalker.exe','jabswitch.exe',
                         'java-rmi.exe','jfr.exe','jhsdb.exe','jinfo.exe','jmap.exe',
                         'jstack.exe','jstatd.exe','kinit.exe','klist.exe','ktab.exe')
            $exe = Get-ChildItem "$binDir\*.exe" -ErrorAction SilentlyContinue |
                   Where-Object { $exclude -notcontains $_.Name.ToLower() } |
                   Select-Object -First 1
            if ($exe) { return $exe.FullName }
        }

        $exe = Get-ChildItem "$($item.FullName)\*.exe" -ErrorAction SilentlyContinue |
               Select-Object -First 1
        if ($exe) { return $exe.FullName }

        return $null
    }

    if ($item.Extension -ieq ".exe") {
        return $item.FullName
    }

    return $null
}

function Find-JavaExe {
    $candidates = New-Object System.Collections.Generic.List[string]

    if ($JAVA_HOME_OVERRIDE) {
        $resolved = Resolve-JavaPath -InputPath $JAVA_HOME_OVERRIDE
        if ($resolved) { $candidates.Add($resolved) | Out-Null }
    }

    if ($env:GHIDRA_JAVA_HOME) {
        $resolved = Resolve-JavaPath -InputPath $env:GHIDRA_JAVA_HOME
        if ($resolved) { $candidates.Add($resolved) | Out-Null }
    }

    if ($env:JAVA_HOME) {
        $c = Join-Path $env:JAVA_HOME "bin\java.exe"
        if (Test-Path $c) { $candidates.Add($c) | Out-Null }
    }

    $portablePatterns = @(
        "$env:USERPROFILE\Documents\jdk*\bin\*.exe",
        "$env:USERPROFILE\Documents\jdk-*\bin\*.exe",
        "$env:USERPROFILE\Desktop\jdk*\bin\*.exe",
        "$env:USERPROFILE\jdk*\bin\*.exe",
        "$env:USERPROFILE\jdk-*\bin\*.exe",
        "$env:USERPROFILE\.jdks\*\bin\java.exe",
        "$env:LOCALAPPDATA\Programs\Eclipse Adoptium\*\bin\java.exe",
        "$env:LOCALAPPDATA\Programs\Microsoft\jdk-*\bin\java.exe",
        "$env:LOCALAPPDATA\Programs\Java\jdk-*\bin\java.exe"
    )
    foreach ($p in $portablePatterns) {
        Get-ChildItem $p -ErrorAction SilentlyContinue | ForEach-Object {
            $candidates.Add($_.FullName) | Out-Null
        }
    }

    $systemPatterns = @(
        "$env:ProgramFiles\Eclipse Adoptium\*\bin\java.exe",
        "$env:ProgramFiles\Java\jdk-*\bin\java.exe",
        "$env:ProgramFiles\Microsoft\jdk-*\bin\java.exe",
        "$env:ProgramFiles\Amazon Corretto\*\bin\java.exe",
        "$env:ProgramFiles\BellSoft\LibericaJDK-*\bin\java.exe"
    )
    foreach ($p in $systemPatterns) {
        Get-ChildItem $p -ErrorAction SilentlyContinue | ForEach-Object {
            $candidates.Add($_.FullName) | Out-Null
        }
    }

    $cmd = Get-Command java.exe -ErrorAction SilentlyContinue
    if ($cmd -and $cmd.Source -notmatch 'javapath') {
        $candidates.Add($cmd.Source) | Out-Null
    }

    $seen = @{}
    $unique = @()
    foreach ($c in $candidates) {
        if (-not $c) { continue }
        $key = $c.ToLower()
        if (-not $seen.ContainsKey($key)) {
            $seen[$key] = $true
            $unique += $c
        }
    }

    if ($JAVA_HOME_OVERRIDE) {
        $forced = Resolve-JavaPath -InputPath $JAVA_HOME_OVERRIDE
        if (-not $forced) {
            Write-Host ""
            Write-Host "ERREUR : impossible de trouver un java.exe valide." -ForegroundColor Red
            Write-Host "  Entrée : $JAVA_HOME_OVERRIDE" -ForegroundColor Yellow
            exit 1
        }
        $major = Get-JavaMajorVersion -JavaExe $forced
        if ($major -lt $MIN_JAVA_MAJOR) {
            Write-Host ""
            Write-Host "ERREUR : version Java trop ancienne." -ForegroundColor Red
            Write-Host "  Chemin  : $forced" -ForegroundColor Yellow
            Write-Host "  Version : $major (minimum requis : $MIN_JAVA_MAJOR)" -ForegroundColor Yellow
            exit 1
        }
        return @{ Path = $forced; Major = $major }
    }

    $tooOld = @()
    foreach ($c in $unique) {
        if (-not (Test-Path $c)) { continue }
        $major = Get-JavaMajorVersion -JavaExe $c
        if ($major -ge $MIN_JAVA_MAJOR) {
            return @{ Path = $c; Major = $major }
        } elseif ($major -gt 0) {
            $tooOld += "$c (Java $major)"
        }
    }

    Write-Host ""
    Write-Host "ERREUR : aucun JDK $MIN_JAVA_MAJOR+ trouvé." -ForegroundColor Red
    if ($tooOld.Count -gt 0) {
        Write-Host "Versions trop anciennes détectées :" -ForegroundColor Yellow
        $tooOld | ForEach-Object { Write-Host "  - $_" -ForegroundColor Yellow }
    }
    exit 1
}

Erreur 1 — UnsupportedClassVersionError

Au lancement, Java refuse d'exécuter Ghidra car il est trop ancien :

Diagnostic

  • class file version 65.0 = Java 21 (ce que Ghidra attend)

Erreur 2 — Le stub Oracle javapath

Le script affichait :

Java : C:\Program Files (x86)\Common Files\Oracle\Java\javapath\java.exe

Ce chemin est un faux Java installé par Oracle qui pointe vers une JRE 8. Il est placé dans le PATH système avant toute autre installation.

✅ Solution Le script exclut désormais les chemins contenant javapath : 
if ($cmd -and $cmd.Source -notmatch 'javapath') {
    $candidates.Add($cmd.Source) | Out-Null
}

Erreur 3 — java.exe renommé (contrôle parental)

Si java.exe est bloqué par un contrôle parental ou une politique, tu peux le renommer (par exemple java_perso.exe). Le script doit pouvoir accepter ce nouveau nom.

✅ Solution Le script accepte maintenant soit un dossier JDK, soit un fichier .exe direct, et scanne le dossier bin\ à la recherche de n'importe quel .exe (en excluant les outils JDK connus comme javac.exe, jar.exe, etc.). 
# Les deux fonctionnent :
$JAVA_HOME_OVERRIDE = "C:\...\jdk-25.0.4"
$JAVA_HOME_OVERRIDE = "C:\...\jdk-25.0.4\bin\java_perso.exe"

Erreur 4 — Version : 0 (bug PowerShell)

Après avoir ajouté la vérification de version, le script affichait :

ERREUR : version Java trop ancienne. Chemin : C:\Users\simon\OneDrive - OGEC LILLE\loisir\java\java 25\jdk-25.0.4\bin\java.exe Version : 0 (minimum requis : 21)

Pourtant ce Java est bien un Java 25.

Diagnostic

java -version écrit sa sortie sur stderr (pas stdout). Avec $ErrorActionPreference = "Stop" en haut du script, PowerShell considérait cette sortie comme une erreur fatale, le try/catch l'avalait, et la fonction retournait 0.

✅ Solution On lance Java via System.Diagnostics.Process avec RedirectStandardError = $true, ce qui contourne complètement le système d'erreur de PowerShell : 
$psi = New-Object System.Diagnostics.ProcessStartInfo
$psi.FileName               = $JavaExe
$psi.Arguments              = "-version"
$psi.RedirectStandardError  = $true
$psi.RedirectStandardOutput = $true
$psi.UseShellExecute        = $false
$psi.CreateNoWindow         = $true

$proc = [System.Diagnostics.Process]::Start($psi)
$stderr = $proc.StandardError.ReadToEnd()
$stdout = $proc.StandardOutput.ReadToEnd()
$proc.WaitForExit()

$combined = $stderr + "`n" + $stdout
# Puis regex sur $combined
💡 Leçon Ne jamais utiliser & $exe args directement pour lire la sortie d'un exécutable qui écrit sur stderr, surtout avec $ErrorActionPreference = "Stop".

Erreur 5 — Java 25 accepté ?

Question légitime : Ghidra 12.x est compilé pour Java 21 (class file 65.0). Est-ce qu'un Java 25 (class file 69.0) peut l'exécuter ?

✅ Oui, sans problème Java est rétrocompatible à sens unique :
  • Un JVM Java 25 peut exécuter du bytecode compilé pour Java 21, 17, 11… ✅
  • Un JVM Java 8 ne peut PAS exécuter du bytecode Java 21 ❌ (c'est l'erreur UnsupportedClassVersionError)
Donc $MIN_JAVA_MAJOR = 21 et accepter tout ce qui est ≥ 21 est correct.

Erreur 6 — Main method not found in class ghidra.GhidraRun

Après avoir corrigé Java, le script lançait bien Java mais Ghidra refusait de démarrer :

Error: Main method not found in class ghidra.GhidraRun, please define the main method as: public static void main(String[] args) or a JavaFX application class must extend javafx.application.Application

Diagnostic

Il est tentant de croire que ghidra.GhidraRun est la classe principale de Ghidra. C'est faux. C'est en réalité une classe utilitaire qui n'a pas de main(). Le vrai point d'entrée est ghidra.Ghidra, qui a deux rôles :

  1. Installer le GhidraClassLoader personnalisé au démarrage du JVM (via -Djava.system.class.loader).
  2. Déléguer à la classe passée en argument (ici ghidra.GhidraRun pour l'interface graphique).

De plus, le classpath ne doit contenir qu'un seul JAR : Utility.jar. Le reste est découvert dynamiquement par le class loader au runtime.

Commande correcte

java -Djava.system.class.loader=ghidra.GhidraClassLoader \
     -cp "Ghidra\Framework\Utility\lib\Utility.jar" \
     ghidra.Ghidra ghidra.GhidraRun

Comparaison avant / après

Avant (incorrect)Après (correct)
-cp "$classpath" (154 JARs)-cp "$utilityJar" (1 seul JAR)
Classe main : ghidra.GhidraRunClasse main : ghidra.Ghidra
Argument : aucunArgument : ghidra.GhidraRun
Aucun -Djava.system.class.loader-Djava.system.class.loader=ghidra.GhidraClassLoader
✅ Solution Le script PowerShell final localise Utility.jar, ajoute l'argument JVM du class loader, et passe ghidra.Ghidra ghidra.GhidraRun comme classe principale + argument.

Erreur 7 — Le script ne trouve aucun JAR

Si tu vois :

ERREUR : aucun JAR trouvé dans C:\...\ghidra_12.1.4_PUBLIC.
✅ Vérifications
  • Le dossier doit contenir un sous-dossier Ghidra\ (attention à la casse : Ghidra, pas ghidra).
  • Le sous-dossier Ghidra\ doit contenir des catégories (Features, Framework, Processors…).

Erreur 8 — Utility.jar introuvable

Le script a trouvé les JARs mais n'arrive pas à localiser Utility.jar.

✅ Solution Le script cherche d'abord à l'emplacement standard : 
$GhidraDir\Ghidra\Framework\Utility\lib\Utility.jar
Puis, en fallback, il fait une recherche récursive dans $GhidraDir\Ghidra\. Si tu vois ce message, c'est que la structure de l'installation est inhabituelle — vérifie que Utility.jar existe bien quelque part.

Erreur 9 — Impossible de charger le fichier ... car l'exécution de scripts est désactivée

Erreur classique de PowerShell au lancement d'un .ps1.

✅ Solution Utilise -ExecutionPolicy Bypass :

Cette option n'a pas besoin de droits admin et ne modifie rien de permanent.

Guide Ghidra Complet

Maîtriser le reverse engineering avec Ghidra : installation, utilisation, debugging, scripting, et solutions aux problèmes rencontrés en environnement restreint.

Introduction

Ghidra est un framework de reverse engineering développé par la NSA, publié en open source en 2019. Il permet d'analyser des binaires compilés et de reconstruire du pseudo-code à partir d'assembleur. Il est comparable à IDA Pro ou radare2, mais entièrement gratuit et extensible.

Capacités principales : désassemblage, décompilation, graphes, scripting (Java/Python), debugging, version tracking, analyse comportementale (BSim), et bien plus.

⚠️ Avertissement légal N'analyse que des binaires que tu possèdes, que tu as écrits, ou pour lesquels tu as une autorisation explicite (CTF, crackmes.one). Le reverse engineering de logiciels tiers peut violer les conditions d'utilisation ou la loi selon les pays.

1. Installation & prérequis

15. Installation sans droits admin & contournement de restrictions

Sur un poste d'entreprise ou une machine verrouillée, plusieurs restrictions peuvent empêcher Ghidra de démarrer :

  • Pas de droits administrateur
  • cmd.exe bloqué par stratégie de groupe
  • Fichiers .bat et .cmd bloqués (AppLocker, SRP, WDAC)
  • java.exe bloqué par contrôle parental ou autre
  • Windows PowerShell soumis à une ExecutionPolicy restrictive

Stratégie générale

PowerShell est presque toujours disponible même quand cmd.exe est bloqué. On va donc réimplémenter entièrement ghidraRun.bat en PowerShell, sans jamais invoquer cmd.exe.

⚠️ Pourquoi ne pas juste appeler le .bat depuis PowerShell ? Si le blocage est fait par AppLocker/SRP/WDAC, c'est le noyau Windows qui refuse d'exécuter un .bat, peu importe qui l'appelle. Il faut rejouer la logique du script en pur PowerShell.

function Get-JavaMajorVersion {
    param([string]$JavaExe)

    # On lance Java via System.Diagnostics.Process pour contourner
    # complètement la gestion d'erreur de PowerShell (java -version
    # écrit sur stderr, ce qui déclenche $ErrorActionPreference = "Stop").
    try {
        $psi = New-Object System.Diagnostics.ProcessStartInfo
        $psi.FileName               = $JavaExe
        $psi.Arguments              = "-version"
        $psi.RedirectStandardError  = $true
        $psi.RedirectStandardOutput = $true
        $psi.UseShellExecute        = $false
        $psi.CreateNoWindow         = $true

        $proc = [System.Diagnostics.Process]::Start($psi)
        $stderr = $proc.StandardError.ReadToEnd()
        $stdout = $proc.StandardOutput.ReadToEnd()
        $proc.WaitForExit()

        $combined = $stderr + "`n" + $stdout

        if ($combined -match 'version\s+"(\d+)') {
            $major = [int]$Matches[1]
            # Cas spécial : "1.8.0_xxx" → on veut 8, pas 1
            if ($major -eq 1 -and $combined -match 'version\s+"1\.(\d+)') {
                $major = [int]$Matches[1]
            }
            return $major
        }
    } catch { }

    return 0
}

function Resolve-JavaPath {
    param([string]$InputPath)

    if (-not $InputPath) { return $null }
    if (-not (Test-Path $InputPath)) { return $null }

    $item = Get-Item $InputPath -ErrorAction SilentlyContinue
    if (-not $item) { return $null }

    if ($item.PSIsContainer) {
        $c1 = Join-Path $item.FullName "bin\java.exe"
        if (Test-Path $c1) { return $c1 }

        $c2 = Join-Path $item.FullName "bin\javaw.exe"
        if (Test-Path $c2) { return $c2 }

        $binDir = Join-Path $item.FullName "bin"
        if (Test-Path $binDir) {
            $exclude = @('javac.exe','jar.exe','jarsigner.exe','javadoc.exe','jdb.exe',
                         'jps.exe','jstat.exe','jcmd.exe','jconsole.exe','jlink.exe',
                         'jmod.exe','jrunscript.exe','jshell.exe','keytool.exe',
                         'policytool.exe','rmid.exe','rmiregistry.exe','serialver.exe',
                         'jaccessinspector.exe','jaccesswalker.exe','jabswitch.exe',
                         'java-rmi.exe','jfr.exe','jhsdb.exe','jinfo.exe','jmap.exe',
                         'jstack.exe','jstatd.exe','kinit.exe','klist.exe','ktab.exe')
            $exe = Get-ChildItem "$binDir\*.exe" -ErrorAction SilentlyContinue |
                   Where-Object { $exclude -notcontains $_.Name.ToLower() } |
                   Select-Object -First 1
            if ($exe) { return $exe.FullName }
        }

        $exe = Get-ChildItem "$($item.FullName)\*.exe" -ErrorAction SilentlyContinue |
               Select-Object -First 1
        if ($exe) { return $exe.FullName }

        return $null
    }

    if ($item.Extension -ieq ".exe") {
        return $item.FullName
    }

    return $null
}

function Find-JavaExe {
    $candidates = New-Object System.Collections.Generic.List[string]

    if ($JAVA_HOME_OVERRIDE) {
        $resolved = Resolve-JavaPath -InputPath $JAVA_HOME_OVERRIDE
        if ($resolved) { $candidates.Add($resolved) | Out-Null }
    }

    if ($env:GHIDRA_JAVA_HOME) {
        $resolved = Resolve-JavaPath -InputPath $env:GHIDRA_JAVA_HOME
        if ($resolved) { $candidates.Add($resolved) | Out-Null }
    }

    if ($env:JAVA_HOME) {
        $c = Join-Path $env:JAVA_HOME "bin\java.exe"
        if (Test-Path $c) { $candidates.Add($c) | Out-Null }
    }

    $portablePatterns = @(
        "$env:USERPROFILE\Documents\jdk*\bin\*.exe",
        "$env:USERPROFILE\Documents\jdk-*\bin\*.exe",
        "$env:USERPROFILE\Desktop\jdk*\bin\*.exe",
        "$env:USERPROFILE\jdk*\bin\*.exe",
        "$env:USERPROFILE\jdk-*\bin\*.exe",
        "$env:USERPROFILE\.jdks\*\bin\java.exe",

            return @{ Path = $c; Major = $major }

            $tooOld += "$c (Java $major)"
        }

15.1 Erreurs rencontrées & solutions

Voici tous les problèmes rencontrés lors de la mise en place du launcher PowerShell, avec leur diagnostic et leur correctif.

Erreur 1 — UnsupportedClassVersionError

Au lancement, Java refuse d'exécuter Ghidra car il est trop ancien :

Error: A JNI error has occurred, please check your installation and try again Exception in thread "main" java.lang.UnsupportedClassVersionError: ghidra/GhidraRun has been compiled by a more recent version of the Java Runtime (class file version 65.0), this version of the Java Runtime only recognizes class file versions up to 52.0

Diagnostic

  • class file version 65.0 = Java 21 (ce que Ghidra attend)
  • class file version 52.0 = Java 8 (ce que ton système a lancé)

Table de correspondance

✅ Solution Utilise la variable $JAVA_HOME_OVERRIDE en haut du script pour pointer explicitement vers ton JDK 21+ : 
$JAVA_HOME_OVERRIDE = "C:\Users\simon\Documents\jdk-21.0.5+11"

Erreur 2 — Le stub Oracle javapath

Le script affichait :

Java : C:\Program Files (x86)\Common Files\Oracle\Java\javapath\java.exe

Ce chemin est un faux Java installé par Oracle qui pointe vers une JRE 8. Il est placé dans le PATH système avant toute autre installation.

✅ Solution Le script exclut désormais les chemins contenant javapath : 
if ($cmd -and $cmd.Source -notmatch 'javapath') {
    $candidates.Add($cmd.Source) | Out-Null
}

Erreur 3 — java.exe renommé (contrôle parental)

Si java.exe est bloqué par un contrôle parental ou une politique, tu peux le renommer (par exemple java_perso.exe). Le script doit pouvoir accepter ce nouveau nom.

✅ Solution Le script accepte maintenant soit un dossier JDK, soit un fichier .exe direct, et scanne le dossier bin\ à la recherche de n'importe quel .exe (en excluant les outils JDK connus comme javac.exe, jar.exe, etc.). 
# Les deux fonctionnent :
$JAVA_HOME_OVERRIDE = "C:\...\jdk-25.0.4"
$JAVA_HOME_OVERRIDE = "C:\...\jdk-25.0.4\bin\java_perso.exe"

Erreur 4 — Version : 0 (bug PowerShell)

Après avoir ajouté la vérification de version, le script affichait :

ERREUR : version Java trop ancienne. Chemin : C:\Users\simon\OneDrive - OGEC LILLE\loisir\java\java 25\jdk-25.0.4\bin\java.exe Version : 0 (minimum requis : 21)

Pourtant ce Java est bien un Java 25.

Diagnostic

java -version écrit sa sortie sur stderr (pas stdout). Avec $ErrorActionPreference = "Stop" en haut du script, PowerShell considérait cette sortie comme une erreur fatale, le try/catch l'avalait, et la fonction retournait 0.

✅ Solution On lance Java via System.Diagnostics.Process avec RedirectStandardError = $true, ce qui contourne complètement le système d'erreur de PowerShell : 
$psi = New-Object System.Diagnostics.ProcessStartInfo
$psi.FileName               = $JavaExe
$psi.Arguments              = "-version"
$psi.RedirectStandardError  = $true
$psi.RedirectStandardOutput = $true
$psi.UseShellExecute        = $false
$psi.CreateNoWindow         = $true

$proc = [System.Diagnostics.Process]::Start($psi)
$stderr = $proc.StandardError.ReadToEnd()
$stdout = $proc.StandardOutput.ReadToEnd()
$proc.WaitForExit()

$combined = $stderr + "`n" + $stdout
# Puis regex sur $combined
💡 Leçon Ne jamais utiliser & $exe args directement pour lire la sortie d'un exécutable qui écrit sur stderr, surtout avec $ErrorActionPreference = "Stop".

Erreur 5 — Java 25 accepté ?

Question légitime : Ghidra 12.x est compilé pour Java 21 (class file 65.0). Est-ce qu'un Java 25 (class file 69.0) peut l'exécuter ?

✅ Oui, sans problème Java est rétrocompatible à sens unique :
  • Un JVM Java 25 peut exécuter du bytecode compilé pour Java 21, 17, 11… ✅
  • Un JVM Java 8 ne peut PAS exécuter du bytecode Java 21 ❌ (c'est l'erreur UnsupportedClassVersionError)
Donc $MIN_JAVA_MAJOR = 21 et accepter tout ce qui est ≥ 21 est correct.

Erreur 6 — Main method not found in class ghidra.GhidraRun

Après avoir corrigé Java, le script lançait bien Java mais Ghidra refusait de démarrer :

Error: Main method not found in class ghidra.GhidraRun, please define the main method as: public static void main(String[] args) or a JavaFX application class must extend javafx.application.Application

Diagnostic

Il est tentant de croire que ghidra.GhidraRun est la classe principale de Ghidra. C'est faux. C'est en réalité une classe utilitaire qui n'a pas de main(). Le vrai point d'entrée est ghidra.Ghidra, qui a deux rôles :

  1. Installer le GhidraClassLoader personnalisé au démarrage du JVM (via -Djava.system.class.loader).
  2. Déléguer à la classe passée en argument (ici ghidra.GhidraRun pour l'interface graphique).

De plus, le classpath ne doit contenir qu'un seul JAR : Utility.jar. Le reste est découvert dynamiquement par le class loader au runtime.

Commande correcte

java -Djava.system.class.loader=ghidra.GhidraClassLoader \
     -cp "Ghidra\Framework\Utility\lib\Utility.jar" \
     ghidra.Ghidra ghidra.GhidraRun

✅ Solution Le script PowerShell final localise Utility.jar, ajoute l'argument JVM du class loader, et passe ghidra.Ghidra ghidra.GhidraRun comme classe principale + argument.

Erreur 7 — Le script ne trouve aucun JAR

Si tu vois :

ERREUR : aucun JAR trouvé dans C:\...\ghidra_12.1.4_PUBLIC.
✅ Vérifications
  • Le dossier doit contenir un sous-dossier Ghidra\ (attention à la casse : Ghidra, pas ghidra).
  • Le sous-dossier Ghidra\ doit contenir des catégories (Features, Framework, Processors…).
  • Chaque module doit avoir un sous-dossier lib\ avec des fichiers .jar.

Erreur 8 — Utility.jar introuvable

Le script a trouvé les JARs mais n'arrive pas à localiser Utility.jar.

✅ Solution Le script cherche d'abord à l'emplacement standard : 
$GhidraDir\Ghidra\Framework\Utility\lib\Utility.jar
Puis, en fallback, il fait une recherche récursive dans $GhidraDir\Ghidra\. Si tu vois ce message, c'est que la structure de l'installation est inhabituelle — vérifie que Utility.jar existe bien quelque part.

Erreur 9 — Impossible de charger le fichier ... car l'exécution de scripts est désactivée

Erreur classique de PowerShell au lancement d'un .ps1.

✅ Solution Utilise -ExecutionPolicy Bypass : 
powershell -ExecutionPolicy Bypass -File .\ghidraRun.ps1
Cette option n'a pas besoin de droits admin et ne modifie rien de permanent.

Erreur 10 — Start-Process : Accès refusé

Si le lancement de Java échoue avec un accès refusé.

✅ Causes possibles
  • Antivirus qui bloque l'exécution de java.exe renommé → ajoute une exception.
  • Contrôle parental → l'exe renommé contourne parfois, sinon change de nom à nouveau.
  • Le fichier a été bloqué par Windows (marqué "non approuvé") : clic droit sur l'exe → Propriétés → Débloquer.
